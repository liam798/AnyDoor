# SDK 源码接入规范

本规范定义第三方 SDK 如何在 AnyDoor 之上提供源码级业务 API。
“必须”是协议或接入要求，“建议”是默认设计选择。示例使用 ADS 模块，不包含真实广告 SDK。

## 方案与命名

统一称为“SDK 源码 API 接入”。SDK 维护者提供调用封装源码，APP 将其纳入自身源码编译；
SDK 内部维护对应处理器。无需单独的协议依赖模块、compileOnly 桩、代码生成器或字节码改写。
源码仍会编译进 APP，不能宣传为零运行时代码或零 IPC 开销。

| 对象 | 命名约定 | ADS 示例 |
| --- | --- | --- |
| 业务模块 | 文档中可使用缩写 | ADS |
| 面向 APP 的调用封装 | `<模块名>Api` | `AdsApi`，文件 `AdsApi.kt` |
| 公开方法 | 业务语义、小驼峰 | `isReady(placement)` |
| 命令 ID | `<命名空间>.v<主版本>.<操作>` | `example.ads.v1.isReady` |

面向 APP 的调用封装不使用 ADSAPI、ADSHelper、AdsManager 等模糊或重复入口。
其他模块按相同规则命名，例如 PaymentApi、AccountApi。
Api 是面向业务的调用入口。SDK 内部类名、文件名、方法名、分层和组织方式由 SDK 自定，
不要求单独建类，也不要求使用 Endpoint 等后缀；只需遵守通信协议及处理器生命周期要求。

## 依赖与所有权

```text
APP 业务 -> AdsApi 源码 -> AnyDoor -> SDK 注册的处理器 -> SDK 实现
```

SDK 维护者同时维护 AdsApi 源码、SDK 接入实现和协议说明，不能让 APP 自行猜测命令或参数。
AdsApi 仅依赖 AnyDoor 根包公开 API及必要的平台/语言类型，不导入 AnyDoor.internal 或 SDK 实现类。
SDK 实现包不应再携带一份相同全限定名的 AdsApi，避免 APP 纳入源码后产生重复类。

第三方源码使用第三方自己的稳定包名，不放入 `com.anydoor`。
同一 APP 中，相同命令 ID 必须只有一个业务所有者；AnyDoor 责任链不用于随机选择广告供应商。
多供应商使用不同命名空间，或由 SDK 接入实现明确聚合。

AnyDoor 不负责业务能力发现、广告保活、主线程切换或广告事件订阅。
此方案完全沿用当前 AnyDoor 调用路径，不增加直接 AIDL 或独立服务池。

## 必交付内容

每次 SDK 发布必须同时交付：

1. 可直接纳入 APP 的 `<模块名>Api.kt`，以及确实必要的源码文件清单。
2. 接入清单：源码版本、兼容 SDK 版本范围、测试过的 AnyDoor 版本、包名和入口。
3. 逐方法协议表：命令 ID、参数、返回值、失败行为、线程要求、是否有副作用。
4. SDK 端注册与注销时机、进程位置、重启后恢复责任。
5. 客户端与实现端的协议一致性测试及迁移说明。

APP 不应私自改命令或返回结构。业务定制应在 APP 外层包装，升级时以 SDK 提供的源码为准。
SDK 同进程还是子进程运行不会改变其是否需要进入最终 APK；源码 API 只解耦调用依赖。

## 协议规则

### 命令与版本

- 命令 ID 必须是显式、固定字符串，不从类名、方法名或反射结果派生。
- 示例命名空间 `example.ads` 是占位值；接入时两端同步换为业务所有者的唯一命名空间。
- SDK 版本、源码版本与协议主版本是三个概念，必须分别说明。
- 修改参数类型、字段含义、返回类型或错误语义等破坏性变更，必须使用新的协议主版本。
- 新增方法可以沿用主版本，但 SDK 维护者必须声明从哪个实现版本开始支持。
- 允许扩展字段的 Map 协议必须事先定义默认值和未知字段处理方式，不能临时假定兼容。
- 缺失命令不能解释成业务 false，也不能用于推断 SDK 精确版本；可选能力需要显式版本/能力协商方法。

### 类型与结果

- 公共方法提供明确参数和返回类型，不向业务暴露 Any? 或原始命令分发入口。
- 单一参数优先使用基础类型；确有多字段需求再定义有文档的 Map/Bundle。
- 必须遵循 [AnyDoor 载荷限制](API与接入.md)，不通过参数传 Activity、View、Context、lambda 或业务实例引用。
- 不使用需要 APP 依赖真实 SDK 实现才能加载的载荷类。
- 对有返回值的方法，处理器返回 CallResult.DoneWith；只有明确“不消费该命令”才返回 Skip。
- 本规范中直接返回标量的方法不允许业务成功返回 null。可空结果必须单独定义可区分的响应结构。
- 对有副作用且需要确认成功的方法，定义明确的业务确认结果，不能把 CallResult.Done 对应的 null 当成功。

### 失败

当前 AnyDoor.call 的 null 可能表示未注册、全部 Skip、无结果或调用异常。
源码 API 必须把缺失结果视为“未获得有效响应”，不能猜测具体原因，也不能默认映射成 false、0 或空集合。
初始化和服务发现异常可能直接抛出，Api 不应吞掉这些异常。
若业务需要区分错误码，必须在该模块协议中另行定义响应结构；AnyDoor 目前没有统一错误码协议。

示例同步 API 约定：

| 情况 | 行为 |
| --- | --- |
| placement 为空白 | 本地抛 IllegalArgumentException，不发送请求 |
| 初始化/发现失败 | 传播 AnyDoor 抛出的异常 |
| 未获得响应 | 抛 IllegalStateException，不承诺根因 |
| 返回类型不是 Boolean | 抛 IllegalStateException，表示协议不匹配 |
| 有效返回 false | 正常业务结果，表示未就绪 |

禁止因 null、false 或通信中断自动重试有副作用操作。一次失败的回包不证明远端没有执行。
需要重试时，模块必须先设计业务幂等标识和重复处理约定，不能靠通信层猜测。

## 线程与生命周期

- 文档必须说明每个公开方法在哪类线程调用。示例 isReady 是同步 IPC，只在工作线程调用。
- Api 默认不持有 Context、Activity、View 或后台线程，不替代 APP 的初始化和生命周期管理。
- SDK 接入实现必须在 SDK 指定进程中注册处理器，保存处理器实例，并用同一实例注销。
- SDK 初始化成功不等于协议注册成功；当前 registerHandler 无成功返回值，不能声明已得到注册确认。
- 中心重启后显式重新注册；处理器进程重启后重新初始化并注册。不自动恢复业务请求。
- 同步调用可并发，也可与异步队列并发；处理器及其调用的 SDK 实现必须满足线程安全要求。
- SDK 要求主线程的能力，由 SDK 端按其生命周期规则处理，不能在 Binder 线程直接操作 UI。
- 不在处理器或回调内阻塞等待同一串行队列中的另一个请求。

异步方法名建议为 `<操作>Async`，但它不保证提交完全非阻塞。
必须分别说明“提交是否接受”“业务是否完成”“结果回调是否收到”；
AnyDoor.callAsync 的 Boolean 只能表达提交结果，进程退出时不能保证回调。
需要多次事件的加载、展示、点击、关闭、奖励协议不包含在本示例中，必须另行设计；
不得把 AnyDoor 的一次结果回调冒充事件流，也不得自行加入核心不支持的订阅能力。

## ADS 最小示例

| 字段 | 定义 |
| --- | --- |
| 模块 | ADS |
| 调用入口 | `com.example.ads.api.AdsApi.isReady(placement: String): Boolean` |
| 命令 | `example.ads.v1.isReady` |
| 请求 | 非空白 String，广告位标识，保持原值，不自动裁剪或改大小写 |
| 成功返回 | Boolean；false 是合法业务结果 |
| 副作用 | 无；只查询 SDK 已有就绪状态，不触发加载或展示 |
| 调用线程 | 工作线程 |
| SDK 端实现 | 必须提供线程安全、快速返回的状态查询 |

交付文件：

- [AdsApi.kt](examples/ads/AdsApi.kt)：APP 侧纳入的唯一调用源码。
- [AdsEndpoint.kt](examples/ads/AdsEndpoint.kt)：SDK 维护者参考实现，不要求 APP 引入此文件；类名、文件名和组织方式仅作演示，第三方无需采用。

APP 初始化 AnyDoor，并确保宿主已按 SDK 要求启动与注册实现后：

```kotlin
import com.example.ads.api.AdsApi

val ready = AdsApi.isReady("reward")
```

在本示例中，SDK 端将自己的状态查询传入 AdsEndpoint，在初始化与销毁阶段调用其 register/unregister。
这些内部类名和方法名不是接入要求，SDK 可以直接在现有组件中完成处理器注册与注销。
示例仅演示同步查询；没有广告供应商依赖、真实广告功能或自动进程管理。

## 混淆与源码更新

固定命令字符串与类名解耦；不为了源码分发默认添加整包 Keep。
实际涉及反射或自定义序列化的类型，必须由维护者明确所需规则并进行 R8 验证。
源码同时存在多个副本、同包同名类或 APP 保留旧版命令，均视为接入错误。
示例文件不纳入 AnyDoor 核心发布物，不新增强制 Gradle 模块。
本仓库将这两个示例文件直接纳入本地测试源集，由 `AdsSourceApiTest` 编译和验证；
第三方使用时无需复制测试配置，也无需依赖测试框架。

## 接入验收

- 只依赖 AnyDoor 公开 API即可编译调用源码，APP 不依赖真实 SDK 实现类型。
- 请求字段、固定命令、返回类型、异常行为与协议表逐项一致。
- false 等合法业务结果不会被当作通信失败，缺失响应不会伪装成成功。
- 在真实跨进程环境验证查询、注销、未注册、异常响应、进程退出与显式恢复。
- 验证同进程和跨进程的业务语义一致，不依赖本地对象引用。
- 验证 Release/R8、混淆后的类型加载与必要 Java 调用。
- 用实际负载测量时延、内存和线程；“源码交付”本身不是性能最优的证据。
