# 架构与竞品分析

当前实现是同应用、中心式的命令责任链，不是远程对象框架，也不是跨进程事件广播。
组件职责见 [目录与职责](目录与职责.md)，实际验证状态见 [验证与发布](验证与发布.md)。

## 进程与线程

调用者和处理器可位于应用默认进程或普通子进程。
AnyDoorProvider 托管中心服务，默认位于应用默认进程，也可由 Manifest 指定专用进程。
子进程 A 调用子进程 B 时，中心查找处理器后通过其 Binder 转发；业务仍在注册端进程执行。

| 路径 | 执行行为 |
| --- | --- |
| initialize | 创建连接依赖，不主动发现服务 |
| 首次调用/重连 | 调用线程通过非稳定 Provider 客户端同步获取 Binder，随后释放客户端 |
| 同步调用 | 本地直调或同步 Binder；远端处理器在其 Binder 线程执行 |
| 异步提交 | 仍需同步提交，返回是否入队；不是端到端非阻塞 |
| 异步执行 | 中心单线程排队执行；远端处理器及回调通过同步 Binder 转发 |
| 结果回调 | 同中心时可在中心工作线程，跨进程时在调用端 Binder 线程，不保证主线程 |

同步调用可并发，也可与异步调用并发执行同一处理器。业务代码必须自行保证线程安全。
异步回调可能早于提交方观察到返回值，不能依赖二者的时序。
不要在处理器或回调内同步等待同一串行队列的后续请求，否则可能互相等待。

Provider 不导出并检查同 UID。它是同应用发现入口，而非面向不可信调用方的通用 RPC 网关；
宿主不得将内部 Binder 转交外部应用或自行放宽访问边界。
发现使用 `acquireUnstableContentProviderClient`，避免稳定 Provider 依赖将中心死亡传播到调用进程。
仅在发现阶段遇到 DeadObjectException 时重新获取一次客户端；不会重试业务调用。

## 性能取舍

| 设计 | 收益 | 代价与限制 |
| --- | --- | --- |
| 缓存服务 Binder | 热调用无需再次发现 | 死亡与实际事务之间仍有竞态，不自动重试 |
| 中心责任链 | 注册和调用语义统一 | A、中心、B 分离时比直接连 B 多一跳 |
| 256 个等待槽位 | 请求数量有界 | 不是字节预算，大对象仍可能占用大量内存 |
| 单线程异步 | 入队后的执行顺序明确 | 慢处理器和慢回调会阻塞后续任务 |
| 按命令缓存只读快照 | 不持注册锁运行业务，稳定注册状态下复用列表 | 每次读取仍有短锁；变更后首次读取重建并缓存列表 |
| Map / Serializable 支持 | 载荷接入方便 | 包装、对象图和反序列化成本不固定 |
| 按需恢复连接 | 没有后台轮询线程 | 业务注册恢复由宿主显式执行 |

不将队列容量视为实测最优值，不因“亿级装机”直接引入无锁路由或更大的线程池。
装机规模需要设备覆盖、长期运行和灰度证据；单设备吞吐需要实际载荷与并发基准。
当前未取得重构前后或竞品同场景性能对照，不能宣称性能最佳。

## 相关方案

以下为机制比较，不是维护状态、版本推荐或性能排名。
Andromeda、Hermes 的描述基于项目维护者 README；未进行依赖集成认证或跑分。

| 方案 | 机制 | 选型考虑 |
| --- | --- | --- |
| 原生 AIDL/Binder | 明确的远程接口与事务 | 固定、强类型接口可评估直接连接目标服务，宿主负责发现和生命周期 |
| Android Messenger | 向目标 Handler 投递跨进程消息 | 适合消息式串行处理，责任链和请求结果关联需自行设计 |
| Andromeda | 本地/远程服务发现、IPC 回调、事件、生命周期集成 | 功能范围更广，接入复杂度和构建集成需另行验证 |
| Hermes | 接口/注解驱动远程方法与对象访问，README 描述 JSON 传输 | 更接近远程对象模型，需评估对象及回调生命周期 |
| AnyDoor | 字符串命令 ID、处理器责任链、Parcel 载荷 | 边界小，但不提供强类型业务方法和远程对象管理 |

来源：

- Andromeda 官方 README：`https://github.com/iqiyi/Andromeda/blob/master/README.md`
- Hermes 官方 README：`https://github.com/Xiaofei-it/Hermes/blob/master/README.md`
- Android AIDL 文档：`https://developer.android.com/develop/background-work/services/aidl`

## 未覆盖能力

当前没有 SDK 级超时、取消、自动重放、自动恢复注册或结构化错误回调。
`null` 混合了无处理器、无返回值和调用失败，不能用于准确计算业务成功率。
SDK 已限制自身处理的 Map 嵌套，但不检查 Bundle、Parcelable、Serializable 内部任意对象图。
Binder 大事务、长时间阻塞、压缩后宿主集成仍需专项验证。
是否扩展能力应基于业务需求另行设计，不通过服务类改名暗示已经支持。

## 后续优化顺序

| 优先级 | 问题 | 需要先确定的契约 |
| --- | --- | --- |
| 高 | null/false 难以区分业务结果和通信故障，注册没有确认返回值 | 错误类型、可重试性、源兼容与二进制兼容 |
| 高 | 客户端绑定锁内包含同步注册/注销 IPC | 并发操作的顺序、失败回滚和中心重启时绑定归属 |
| 高 | 厂商真机故障覆盖、长期负载与 R8 验证缺失 | 中心死亡恢复已有 Android 16 模拟器用例，仍需扩展设备与故障时序覆盖 |
| 中 | 队列按请求数量而非字节限制 | 载荷预算、超限返回方式、宿主业务容忍度 |
| 中 | 快照缓存仍有短锁，注册频繁变更时需要重建 | 分别测量读多写少与频繁注册场景，不将分配减少等同于端到端加速 |

call、callAsync、registerHandler、unregisterHandler 已与当前业务语义一致，
不为了统一前缀重命名公开方法。服务名和连接名表达整体角色，调用类型名表达具体契约。
后续首先补行为契约和验证证据，而不是继续增加目录层级或抽象类。
